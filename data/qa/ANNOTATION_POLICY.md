# ANNOTATION POLICY — local holdout v1 (W5-QA)

Версия политики: **1.0** (2026-10-17). Применима к `data/qa/regression_corpus_v1.json` (corpus_version = `v1`)
и к ожиданиям `data/qa/acceptance_scenarios.json`.

## 0. Статус и ограничения (читать первым)

- Это **локальный synthetic holdout команды**, НЕ данные организаторов и НЕ hidden-набор.
  Все строки написаны вручную QA-инженером; ни одна строка не взята из данных организаторов.
- Метрики на нём — **proxy metrics, не официальный hidden score**. Они не заменяют скрытую оценку
  и не должны подаваться как «точность системы».
- Один аннотатор, нет inter-annotator agreement, n ≈ 100 строк → доверительные интервалы широкие
  (скрипт печатает Wilson 95%). Разницу в 2–3 п.п. между итерациями интерпретировать нельзя.
- Источник правил разметки — ТЗ (S1) через контракт `JANA_ADDRESS_CONTRACT_v1.0.md` (C4, C5, C9),
  текст задач W1/W2 и публичный иллюстративный пример (мкр → `street_type`+`street_name`).
  Где эти источники молчат — случай помечен `unscored` (см. §5), gold **не додумывается**.

## 1. Анти-утечка (holdout не для подбора правил)

1. Строки holdout НЕ используются для подбора правил, словарей и порогов парсера/геокодера.
   Авторам W1–W3 holdout не показывается построчно; им передаётся только агрегат.
2. Строки не пересекаются (по точному совпадению и по нормализации S1) с: acceptance-сценариями
   (`acceptance_scenarios.json`), `data/sample_input.json`, `data/demo_input.json`,
   `data/synthetic_corpus_v1.json`. Проверяется `python scripts/eval_holdout.py --validate`.
3. Изменение gold после первого прогона допустимо только как исправление ошибки аннотации
   с повышением версии (`v2`) и записью в changelog ниже. Прежняя версия не перезаписывается.
4. Запрещено: lookup по `id`/по полной строке; holdout не должен попадать в runtime-данные.

Changelog: v1 — первичная разметка 2026-10-17 (gold написан вручную ДО запуска любого парсера).

## 2. Схема записи

```json
{"id":"H001","raw_address":"...","lang":"ru|kz|mixed","tags":["..."],
 "gold":{"city":"...","street_name":"...","house":"..."},   // только НЕ-null поля
 "basis":{"province":"inferred","city":"alias"},            // только НЕ-explicit поля
 "unscored":["street_type"],                                  // исключены из знаменателей
 "note":"..."}
```

- Поле, отсутствующее в `gold`, означает **проверенный null** (аннотатор подтвердил, что значения нет).
  Именно так измеряются false-fill и null precision/recall.
- `unscored` — поля, где разметка спорна/нефиксируема; для них запись не входит в знаменатель.
- `basis` (по полю): `explicit` (по умолчанию: значение буквально в строке), `alias` (в строке есть
  упоминание на другом языке/в другой графике — KZ, латиница — gold записан канонической RU-формой),
  `inferred` (в строке нет, выведено из другой сущности: область из города, город из уникального района).

## 3. Правила по полям (C4)

| Поле | Правило gold |
|---|---|
| `province` | Для городов республиканского значения (Алматы, Астана, Шымкент) = имя города. Иначе полное имя области в форме «Актюбинская область». Явная область в тексте → explicit; из города → inferred. |
| `city` | Каноническая RU-форма именительного падежа (Актобе, Усть-Каменогорск). KZ («Ақтөбе қаласы», «Өскемен») и латиница («Almaty») → `alias`. Слэш-дубль «Актобе/Ақтөбе қаласы» — ОДИН город. Если город выводится только из названия района, которое встречается в нескольких городах → **null** (abstention). Если район уникален (напр. «Сарыаркинский» → Астана) → inferred. |
| `district` | Без слов «район/р-н/ауданы», каноническая RU-прилагательная форма («Ауэзовский»). KZ «Ауэзов ауданы» → `alias`. |
| `living_area` | Название жилого массива / ЖК / микрорайона **только если** рядом есть отдельная типизированная улица (улица+номер дома). Если мкр/ЖК/квартал — единственный локатор, он записывается в `street_type` + `street_name` (как в публичном иллюстративном примере «Мкр Аксай 3а»), `living_area` = null. |
| `street_type` | Нормализованная RU-форма: улица, проспект, переулок, бульвар, шоссе, проезд, набережная, микрорайон, квартал, жилой комплекс, жилой массив. KZ: даңғыл→проспект, көше→улица. Латиница (`st`, `ave`) → `unscored` (отображение не зафиксировано). Вне hidden-метрики (диагностика). |
| `street_name` | **Дословный фрагмент** строки (регистр, падеж, опечатки как есть), без типа улицы, номера дома и деталей. Для мкр/квартала номер/литера, приклеенные к названию, — часть названия («Аксай 3а», «Самал-2»). В обратной записи «66квартал», «12 мкр» название = число. Без хвостовой пунктуации. Канонизация («казибек би» → «Казыбек Би») ЗАПРЕЩЕНА. |
| `house` | Токен дословно: регистр и литера сохраняются («13Б», «247а»), дробь без пробелов вокруг `/` («89/1»). Всегда строка; «1/2» ≠ «1». Корпус/строение/литер как отдельные слова (к1, корп 2) вне 14-польного контракта и не включаются. Экзотика «12/А» — дословно «12/А». |
| `apartment`, `entrance`, `floor` | Цифры дословно как строка: «3-этаж», «3 этаж», «этаж 3» → «3». Если одно и то же поле встречается дважды с РАЗНЫМИ значениями → конфликт: gold = null и поле помечается `unscored` (спорный случай). |
| `landmark` | Ориентир/POI дословно, вместе со словом-типом («магазин Алтын»), до запятой или адресной детали. Не входит в hidden-метрику (C9) — только диагностика; для расплывчатых фраз («рядом с аптекой Нур») → `unscored`. |
| `confidence` | Не размечается и не входит в метрику. |

## 4. Язык (`lang`)

- `ru`: русский текст без казахских маркеров/букв (ә ғ қ ң ө ұ ү һ і) и без латиницы.
- `kz`: казахские маркеры/названия (қаласы, көшесі, даңғылы, үй, пәтер, қабат, ауданы) и казахская графика преобладают.
- `mixed`: смесь RU+KZ в одной строке, билингвальный слэш «Алматы/Алматы қаласы», либо латиница
  (тег `latin`).

## 5. Спорные случаи и abstention

- **Abstention**: имя сущности, которое встречается в нескольких городах/областях и не
  disambiguated текстом, даёт `null` в выводимых полях (город, область). Пример: «Центральный район,
  ул. Мира 5» → district=«Центральный», city=null. Ложное заполнение здесь = false-fill.
- **adjudication-pending** (gold НЕ создаётся): `Актау 15 мкр 22 дом 5 кв 8` (нумерация микрорайона
  15/22 неоднозначна). Для него в acceptance проверяются только минимально доказанные поля
  (`house=5`, `apartment=8`, `street_name` без «кв/дом»); остальное — отложено арбитру/организаторам.
- ЖК как единственный локатор («Алматы, ЖК Нурлы Тау, дом 12») — `street_type`, `street_name`,
  `living_area` в `unscored`: контракт не фиксирует, куда писать название ЖК.
- Нормализация сравнения — правило S1 (скрипт `eval_holdout.py`): `lower()`, знаки пунктуации →
  пробел, схлопывание пробелов. Пунктуация заменяется пробелом, а не удаляется, поэтому «1/2» ≠ «12»
  и «1/2» ≠ «1». Точная реализация организатора неизвестна (TBD) — метрика помечена proxy.
  Дополнительно считается строгое (`exact`) совпадение без нормализации.

## 6. Группы метрики (C9) и что в них входит

- core (60%): `province`, `city`, `street_name`, `house`
- details (25%): `apartment`, `entrance`, `floor`
- explicit reference (15%): `district`, `living_area`
- вне метрики (диагностика): `street_type`, `landmark`, `confidence`

Взвешенный proxy = 0.60·mean(core) + 0.25·mean(details) + 0.15·mean(ref), где mean — простое среднее
per-field accuracy внутри группы. Внутригрупповые веса организаторов неизвестны (TBD) — это допущение.
