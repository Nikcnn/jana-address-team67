# JANA ADDRESS — CONTRACT v1.1 (provisional, owner-approved delta over v1.0)
Дата: 2026-10-18. Статус: PROVISIONAL (не подтверждён организатором). Решение владельца 2026-10-18 (clarify): перейти с atomic reject на item-level обработку невалидных записей.
Всё из CONTRACT v1.0 остаётся в силе, КРОМЕ C3 (заменён ниже) и связанных с ним строк C2/C7, указанных ниже. Основание: ТЗ — «Пропускать записи нельзя — на каждую входную запись должен быть ответ. Если разобрать не удалось, возвращается объект с null в полях и низким confidence».

## C3-v1.1. Невалидные записи: ITEM-LEVEL (заменяет «ATOMIC REJECT»)
Целостные (envelope-level) ошибки НЕ меняются и по-прежнему дают 4xx на весь запрос:
- битый JSON / невалидный UTF-8 / слишком глубокая вложенность → 400 `invalid_json`;
- неизвестный envelope (не массив, не `items|records|addresses`, не одиночная запись) → 422 `invalid_envelope`;
- > 10000 записей → 413; тело parse-batch > 32 MiB → 413 `body_too_large`; upload-файл > 8 MiB → 413;
- JSONL: строка, не являющаяся валидным JSON → 400 `invalid_jsonl` + `line` (без echo содержимого).

Для каждого ЭЛЕМЕНТА массива записей (в т.ч. при одиночной записи и в upload JSON/JSONL) возвращается РОВНО ОДИН 14-польный объект на том же индексе:
1. Элемент — JSON-объект, `raw_address` — строка (кодируемая в UTF-8, без lone surrogate), длина ≤ 3000 символов → обычный разбор. `id`: строка или целое (не bool) → echo без изменений; иначе (отсутствует / null / float / bool / list / dict / строка с lone surrogate) → `id: null`, остальное разбирается как обычно.
2. Элемент — не объект, ИЛИ `raw_address` отсутствует / не строка / строка с lone surrogate → null-запись: `id` по правилу выше (для не-объекта — null), `raw_address: null`, 11 компонентных полей `null`, `confidence: 0.0`.
3. `raw_address` — строка длиной > 3000 символов → null-запись с `raw_address` ДОСЛОВНО как во входе (эхо), 11 полей `null`, `confidence: 0.0` (разбор не выполняется — это защита ограниченного времени, а не отказ batch).
4. Порядок, количество и дубликаты сохраняются (occurrence index); изменение `id` не меняет компоненты/confidence.
5. Аддитивно (не меняет тело ответа): заголовок ответа `X-Jana-Invalid-Items: <N>` присутствует, если N ≥ 1 записей обработано как null-запись по пунктам 2–3; WARNING-лог `invalid_items_degraded` содержит ТОЛЬКО число записей и до 20 индексов, без значений входа. Без заголовка при N = 0.
6. `raw_address: ""` (пустая строка) — валидная строка: обычный путь, null-компоненты, низкий confidence, `raw_address: ""` в эхо.

Следствия для остальных пунктов v1.0:
- C2: «extra keys игнорируются» без изменений; формулировка «id/raw_address обязательны» читается как «обязательны для разбора; при нарушении — null-запись по C3-v1.1».
- C4: тип `raw_address` в выходе — `str | null` (null только в null-записях по п.2); `id` — `str | int | null` (null только в null-записях и при невалидном id).
- C7: коды item-ошибок (`raw_address_not_string`, `id_missing`, … ) больше НЕ возвращаются клиенту; `invalid_items` 422 удалён из публичного поведения.
- UI (C8): строки с `id`/`raw_address` = null отображаются явно как «нет данных (невалидная запись)», не редактируются в id/raw, экспорт сохраняет null.

## Что НЕ меняется
Маршруты и envelope-зеркалирование, лимиты, 14 полей и порядок ключей, null-семантика компонентов, privacy-правила C10, PROV-статус (организатором не подтверждено).
